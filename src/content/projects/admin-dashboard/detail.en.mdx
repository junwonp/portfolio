## Project overview

**"Reusable back-office patterns for SaaS operations"**

This project was an internal B2B SaaS admin dashboard used to operate accounts, subscriptions, product usage, and revenue monitoring. Because it was an internal company system, screenshots and raw business data cannot be shared; this page focuses on the frontend architecture and reusable interaction patterns.

The important part was not a single screen. It was the repeated operational workflow: list data, filter and search it, inspect detail records, create or edit entities, and monitor usage/revenue signals without losing context. I worked on that surface with **TypeScript**, **React**, **React Table**, **MUI**, **TanStack Query**, and **Chart.js**.

## Retrospective

This project is less of a public-facing case study and more about demonstrating the ability to build reliable, high-density internal tools. While internal surfaces like tables, filters, forms, and charts may be less flashy than consumer UIs, they demand strict state management, predictable interactions, and clear component boundaries.

As page count grew, having each screen invent its own table, filter, and mutation logic rapidly increased maintenance overhead. To counteract this, I consciously introduced the following design rules:

- Clear State Boundaries: Adopted a unidirectional data flow of <strong>query state → table state</strong> so that TanStack Query's server state and React Table's UI state would not collide. Filters and sorting were bound to query keys for consistent server-side pagination, while selected rows and active edit form state were kept strictly inside the table component.
- Documented Trade-offs: Documented pros and cons of alternatives (e.g., AG Grid) so the team could reproduce decisions quickly. While heavy grid solutions were considered initially, React Table was chosen for bundle size and UI consistency with MUI, supplementing with react-virtual only when virtualization was needed.
- Standardized Common CRUD Patterns: Standardized the interaction model across list → detail → create/edit flows, accelerating new admin page development. Consequently, creating a new management page dropped from an average of 3 days to approximately half a day.

This experience clearly demonstrated how 'design that simplifies complexity' directly impacts operational availability and team velocity.
